# Contributing

Thanks for helping with teamdiff. Read [AGENTS.md](AGENTS.md) first: it holds the rules every change
follows, including what the app must never show and what must never be committed.

## Build

teamdiff runs on Windows 10 and 11. You need:

- Rust, installed with [rustup](https://rustup.rs). `rust-toolchain.toml` selects the stable
  toolchain with rustfmt and clippy.
- The Visual Studio C++ build tools, which Rust needs on Windows.
- The Microsoft Edge WebView2 Runtime. Windows 11 includes it; on Windows 10, install it from
  [Microsoft](https://developer.microsoft.com/microsoft-edge/webview2/) if it's missing.

Then build and run it:

```
cargo run --release
```

`cargo run -- --demo` shows every screen with made-up players, without the game. Use it to check how a
change looks; Tab moves to the next screen.

## Check

Run the checks in [AGENTS.md](AGENTS.md#checks) before you commit. CI runs the same ones on every pull
request, and checks commit subjects, the pull request title, and the full history for personal data.

## Pull requests

1. Branch from `main`.
2. Make one change, in commits that each build and pass the checks.
3. Write each commit subject as a Conventional Commit with a scope, such as
   `fix(tracker): retry after a 503`.
4. Open a pull request with a title in the same form. Say what changes for someone using teamdiff,
   and how you tested it.

`main` takes merge commits only. Every review thread must be resolved before a pull request merges.

Pull requests that change the build, such as `Cargo.lock`, `.cargo/config.toml` or the toolchain, also
run **Release build**, which builds the release files as a downloadable artifact. It isn't required,
but check that it passed before merging such a pull request. Release builds ship every dependency's
license notice, generated by [cargo-about](https://github.com/EmbarkStudios/cargo-about) from
`about.toml`, and the build fails on a dependency whose license isn't listed there.

## Ship a release

[release-plz](https://release-plz.dev/) keeps a release pull request open, titled
`chore(release): vX.Y.Z`. Every merge to `main` updates it with the next version and the new
`CHANGELOG.md` entries, each linked to its pull request. Before 1.0, a `feat` moves 0.1.0 to 0.2.0,
a `fix` moves 0.2.0 to 0.2.1, and a breaking change, marked with `!` as in `feat(lobby)!: ...`, also
moves the minor version.

release-plz opens that pull request with the workflow's own token, which works only while
**Settings** > **Actions** > **General** > **Allow GitHub Actions to create and approve pull requests**
is on. With it off, the **Update the release pull request** job fails on every push to `main`.

To ship:

1. Open the release pull request and read the changelog. If an entry needs work, edit
   `CHANGELOG.md` on its branch in a signed commit with a scoped subject, such as
   `docs(changelog): reword the lobby entry`. Your push starts its checks.
2. If you made no edit, approve the waiting workflow runs on the pull request's page. A workflow
   opened it, so GitHub holds its checks until someone approves them, and again after each update
   release-plz pushes.
3. Merge it once its checks pass. Don't merge another pull request until the **Release** workflow's
   **Tag** job has finished, or release-plz may propose the same version again.

The **Release** workflow then tags `vX.Y.Z`, builds the zip from the tag, attests it, and
publishes the GitHub release with the files. If building or publishing fails, re-run the failed jobs.
They pick up from the same tag.

The release notes are GitHub's generated notes. They list every pull request with its author, and
welcome first-time contributors by name. The **PR labels** workflow labels each pull request from its
title, and `.github/release.yml` groups the notes by those labels into breaking changes, features,
fixes and other changes.
